Introduction

In this lesson, you'll configure the APM integration with the secret token you discovered in the previous lab. Once the APM Server and OTel Collector share the same authentication token, trace data will begin flowing into your Elastic cluster. This completes the connection between your instrumented applications and Elastic Observability.

**Edit APM Integration settings**

From the previous lab, you learned the value of the secret token used in the OTel Collector configuration.

<img width="1440" height="134" alt="image" src="https://github.com/user-attachments/assets/74319a46-a9ec-4838-8a8a-9129ef05fb23" />

Now, you need to set up the same secret token in the settings of your APM integration in order for trace data to reach your Elastic cluster.

<img width="1321" height="470" alt="image" src="https://github.com/user-attachments/assets/a05d4eb4-c5fc-4bb0-b7b5-1a4159b40537" />

<img width="1321" height="470" alt="image" src="https://github.com/user-attachments/assets/618fb377-3b5c-4236-bb23-e11722c34e45" />

🔍 Why this matters

The secret token acts as a shared secret between the OTel Collector and APM Server. Both sides must have the identical token configured—if they don't match, the APM Server rejects incoming trace data. This is a common configuration issue when setting up observability pipelines.

1. Under the Installed integrations tab, click on the Elastic APM integration.

<img width="2748" height="2164" alt="image" src="https://github.com/user-attachments/assets/a2ccb2ce-c573-40ca-932c-e805e532de5b" />

2. Click the Integration policies tab and then select the apm-1 integration policy.

<img width="2932" height="894" alt="image" src="https://github.com/user-attachments/assets/818253c4-fc79-416d-a7e2-d30fa4bc8469" />

🔍 Why this matters

An integration can have multiple policies for different use cases. The `apm-1` policy is the active configuration that the APM Server is using. Changes to this policy take effect after saving and deploying.

3. In the Integration settings page, scroll down until you find the **Agent authorization** section. Enable API key for agent authentication and set the secret token to `nonprodpwd`.

<img width="1608" height="718" alt="image" src="https://github.com/user-attachments/assets/f3d6c4f9-5938-405d-a865-8682f78adf47" />

⚠️ Use strong tokens in production

The token nonprodpwd is intentionally simple for this lab environment. In production, use a strong, randomly generated token and store it securely. Anyone with this token can send data to your APM Server.

4. Save the modification made to the APM integration by clicking Save integration. Confirm the changes by clicking Save and deploy changes.
  
5. After the changes have been deployed, from the `Kibana` main menu access `Observability > Applications` App.

<img width="484" height="1476" alt="image" src="https://github.com/user-attachments/assets/0b6f94f7-6bcc-4dea-ad53-beee30cbced3" />

6. In the `Services` application you will see the various OTel Demo application components. APM data is generated and collected by the agent running inside the various application components.

<img width="2968" height="2156" alt="image" src="https://github.com/user-attachments/assets/38b27bed-a7b3-4e3a-8658-d145e82543f6" />

🔍 Why this matters

The Services inventory shows all applications sending APM data to your cluster. Each service corresponds to an instrumented microservice in the OTel Demo application. The fact that services appear confirms that the authentication is now working correctly.

**Conclusion**

In this lesson, you configured the APM integration with the correct secret token, enabling authenticated trace data from the OTel Collector to appear in Elastic Observability.
